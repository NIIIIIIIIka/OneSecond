# 一秒不差？· M3（误差排行榜）

一个“凭感觉计时 1 秒”的微信小程序。点击开始后计时完全隐藏，凭感觉按下停止，看看你的误差有多接近 1000ms。

当前为 **M3 版本**：在 M1.1 玩法与 M2 云端个人最佳之上，新增「一秒封神榜」排行榜、个人名次、超越百分比和距上一名差距，形成“挑战 → 看排名 → 再来一局”的循环。**未配置云环境 ID 时，保持纯本地模式，所有原有功能不受影响；排行榜显示“排行榜暂未开放”。**

## 运行方式

1. 安装并打开 [微信开发者工具](https://developers.weixin.qq.com/miniprogram/dev/devtools/download.html)。
2. 选择「导入项目」，目录选择本仓库根目录（包含 `project.config.json` 的那一层）。
3. AppID：使用自己的小程序 AppID 即可；没有的话可以选「测试号」，或把 `project.config.json` 中的 `appid` 改为 `touristappid` 走游客模式。
4. 编译后直接进入挑战页。

云端同步与排行榜是可选的，配置步骤见下文「云开发配置（M2 / M3）」。不配置也能正常游玩。

## 玩法与规则

- 状态流程：待开始 → 准备 → 挑战 → 结果。点击「开始游戏」只进入准备页，点击「开始计时」才真正开始计时。
- 目标时间 1000ms，误差 = |实际用时 − 1000|。
- 有效成绩范围：0–3000ms。超出范围仍展示实际用时与误差，但不计入个人最佳。
- 首次有效挑战自动成为个人最佳；之后只有误差严格更小才刷新。
- 个人最佳保存在本地：`bestError`（误差，兼容旧数据）与 `bestElapsed`（用时，M1.1 新增）。
- 挑战中切换到后台会取消本局，回到准备状态。

### 云端同步规则（M2）

- 结算时本地结果与本地最佳立即更新，随后**异步**提交云端；网络与云函数不会阻塞按钮或结果展示，也不影响计时精度。
- 云端以误差更小的有效成绩为最佳；误差相同时保留云端先前记录（`createdAt` 不变）。
- 云端最佳更优时（例如首次安装或换设备后云端已有记录），本地会自动采用云端成绩。
- 页面可显示三种同步状态：`同步中` / `已同步` / `待同步`。
- 只有云端明确确认后才显示「已同步」；网络失败、云函数未部署、限流等情况一律保持「待同步」。
- 待同步成绩会在下次进入页面、网络恢复或再次挑战时重试；旧请求即使延迟成功，也不会覆盖本地更新的更好成绩，更不会误报「已同步」。
- 云开发未配置时，不显示同步状态，游戏行为与 M1.1 完全一致。
- 只有 `bestElapsed` 存在的成绩才会自动同步；仅有旧版 `bestError` 的历史数据无法确定实际用时，不会被自动提交（再次刷新最佳后会正常同步）。

### 排行榜规则（M3）

- 每个用户仍只有一条云端个人最佳记录，榜单展示的就是这条最佳成绩。
- 总榜展示前 100 名；排序规则固定为：
  1. `error` 升序（误差越小越靠前）；
  2. `createdAt` 升序（相同误差时记录首次创建更早者靠前；刷新最佳不会重置该时间）；
  3. `_id` 升序（前两项完全相同时的确定性 tie-breaker）。
- 名次从 1 开始连续编号，不采用并列跳号。相同误差的两位玩家，`createdAt` 更早（记录首次创建更早）者名次更高。
- 超越百分比：
  - `N > 1` 时：`(N - rank) / (N - 1) × 100%`，保留一位小数；
  - `N = 1` 时显示 `100%`，并提示“目前只有一名上榜玩家”。
- 距上一名差距：`gap = 我的 error - 紧邻上一名的 error`。
  - `gap = 0` 显示“与上一名误差相同，提交时间稍晚”；
  - 第一名显示“你就是第一名”；
  - 没有云端成绩时不返回虚构名次。
- 个人排名通过完整排序规则做**条件计数**得到，不会只读取前 100 名来推算第 100 名以外的用户。
- 展示名采用「挑战者·」加文档哈希前 10 位十六进制字符，稳定、可区分，不返回 openid 或完整文档 ID。
- 榜单页支持下拉刷新、加载中 / 失败 / 空榜状态；前 100 名缓存 60 秒，下拉刷新会强制更新。
- 结果页的排名请求异步执行，不阻塞实际用时展示或重新挑战；网络失败只标记排名暂不可用，不影响本地成绩。用户开始下一局后，上一局的迟到响应会被丢弃。

## 云开发配置（M2 / M3）

以下步骤需要在小程序后台 / 微信开发者工具中手动完成。仓库默认不包含任何云环境 ID、密钥或凭证。

### 1. 开通云开发

1. 用小程序管理员或开发者账号登录微信开发者工具。
2. 点击工具栏「云开发」，按提示开通（选择按量付费或免费额度，具体以控制台为准）。
3. 创建一个环境，记下 **环境 ID**（形如 `one-second-xxxx`）。

### 2. 配置环境 ID

复制 `miniprogram/config/cloud.example.js` 为 `miniprogram/config/cloud.js`，再填写：

```js
module.exports = {
  envId: "你的环境 ID",
};
```

`cloud.js` 是本地配置，已被 `.gitignore` 忽略，不会提交。留空或未创建该文件时保持纯本地模式。环境 ID 本身不是密钥，但建议按团队规范管理，不要提交无关的私有配置。

### 3. 创建 scores 集合

1. 云开发控制台 → 数据库 → 新建集合：`scores`。
2. 权限设置为**所有用户不可读写**。推荐使用自定义安全规则：

```json
{
  "read": false,
  "write": false
}
```

成绩只允许通过云函数读写；云函数使用管理员权限，不受该规则限制。

### 4. 索引

M2 的个人最佳查询依赖确定性文档 ID（`best_<sha256(openid)>`），不需要额外索引。

M3 排名查询需要在云开发控制台为 `scores` 创建组合索引（按顺序）：

1. `error` 升序
2. `createdAt` 升序
3. `_id` 升序（如果控制台允许把 `_id` 加入组合索引；`_id` 本身已有唯一索引）

如果控制台不允许 `_id` 作为组合索引字段，至少创建 `error + createdAt` 组合索引；完全相同误差与创建时间的记录非常少，`_id` 作为最终过滤条件仍能保证确定性排序。索引用于以下查询：

- 前 100 名：`orderBy(error, createdAt, _id).limit(100)`；
- 名次计数：`error <`、`error == 且 createdAt <`、`error == 且 createdAt == 且 _id <`；
- 上一名：按相同排序键反向取 1 条。

说明：微信云数据库不提供任意形式的唯一复合索引；同一用户唯一性由确定性 `_id` 保证。

### 5. 部署云函数

在开发者工具中分别右键以下目录，选择「上传并部署：云端安装依赖」：

- `cloudfunctions/submitScore`
- `cloudfunctions/getMyScore`
- `cloudfunctions/getRank`
- `cloudfunctions/getMyRank`

`project.config.json` 已配置 `"cloudfunctionRoot": "cloudfunctions/"`。四个云函数都依赖 `wx-server-sdk`，由云端安装。只部署 M2 的两个函数时，结果页仍可同步个人最佳，但排名会显示不可用；排行榜页会显示加载失败。

### 6. 验证成绩已写入云端

1. 编译小程序，完成一次有效挑战（0–3000ms）。
2. 云开发控制台 → 数据库 → `scores`，应出现一条记录，字段包括 `_id`、`openid`、`elapsed`、`error`、`createdAt`、`updatedAt`。
3. 再完成一次误差更大的挑战，记录应保持不变；完成误差更小的挑战，记录才会更新。
4. 页面结果区应显示「已同步」或「待同步」；未配置环境 ID 时不显示该状态。

### 7. 验证排行榜

1. 用至少两个微信账号（或开发者工具的多账号调试）分别完成有效挑战，确保 `scores` 中有多条记录。
2. 进入挑战页的「查看一秒封神榜」，应看到按误差升序排列的前 100 名；前三名有金银铜样式，本人所在行高亮。
3. 如果本人不在前 100，页面底部固定显示「我的排名 / 超越百分比 / 距上一名差距」。
4. 结果页在实际用时下方应异步出现排名反馈；重点文案为“距离上一名只差 X ms”。网络断开时结果仍正常显示，排名显示“排名暂不可用”。
5. 点击「再来一局」后，上一局迟到的排名响应不应覆盖新一局页面状态。
6. 空集合时显示“目前无人上榜，第一名等你来拿。”；未配置云环境时显示“排行榜暂未开放”。
7. 相同误差的排序验证：为两个测试账号提交相同误差、不同时间的成绩，先提交者应排在前面。相同误差且相同时间的情况可用控制台手动写入 `createdAt` 相同的两条测试文档验证 `_id` 升序。

### 8. 清理测试数据

- 单条：在数据库控制台删除对应文档。
- 全部：清空或删除 `scores` 集合。删除集合前请确认没有真实用户数据。

### 9. 资源费用与限制

- 云开发按环境计费，包含一定的免费额度；云函数调用、数据库读写与存储均可能产生费用，具体以控制台当前价格为准。
- 本项目仅保存每条用户最佳成绩，数据量很小；仍需关注云函数调用次数与数据库读写次数。
- M3 排名使用 `count()` 与带索引的 `orderBy + limit`，不读取整个集合；前 100 名页面有 60 秒缓存，下拉刷新才强制更新。
- 云函数单次执行、数据库单次查询/更新均有平台限制；本项目只做单文档读写和有限条数的榜单查询，正常使用不会触及上限。
- 不要开启与 M3 无关的付费资源。

## 数据模型

`scores` 集合，每个用户仅一条有效文档：

| 字段 | 说明 |
| --- | --- |
| `_id` | `best_` + `sha256(openid)`，确定性唯一 ID |
| `openid` | 云函数上下文获取的真实用户身份 |
| `elapsed` | 最佳成绩实际用时（ms，0–3000） |
| `error` | 绝对误差 `abs(elapsed - 1000)`，由服务端重新计算 |
| `createdAt` | 成绩记录首次创建时间，服务端生成；后续刷新最佳不改变 |
| `updatedAt` | 记录最后更新时间，服务端生成 |
| `lastSubmitAt` | 最近一次通过的提交时间，用于服务端限流 |

客户端不能指定 `openid`、误差或可信时间戳；昵称、头像等资料不在 M3 范围内。排行榜展示名由服务端根据 `_id` 哈希生成，不返回 `openid` 或完整 `_id`。

## 安全说明与已知限制

- `scores` 集合禁止客户端直接读写，正式成绩只通过云函数写入；排行榜也只通过受控云函数读取，客户端不能直接修改排名。
- 云函数只信任 `cloud.getWXContext().OPENID`，忽略客户端传入的 `openid`。
- 服务端校验 `elapsed` 必须是 0–3000 的整数毫秒，并重新计算 `error`。
- 限流为“同一用户每秒最多一次提交”，基于服务端保存的 `lastSubmitAt`。该实现是**先读后写**，并发请求仍可能同时通过，属于近似限流。
- “更好成绩不被覆盖”采用单文档**条件更新**（`where({ _id, error: gt(newError) }).update(...)`），由数据库在单文档层面保证原子性；首次并发创建使用确定性 `_id` 去重。没有使用事务：M2 只操作单条文档，条件更新已能避免“较差成绩覆盖较好成绩”，事务带来的额外复杂度与限制没有必要。并发首提竞态会跳过限流，以免较好的成绩被另一条首次提交挡住。
- `getRank` 只读取前 100 条并统计总人数；`getMyRank` 用带索引的条件计数计算完整名次，不把整个集合拉到 JavaScript 中排序，也不根据前 100 名推算榜外名次。
- 排名、上一名和总人数是多次查询，**没有使用事务或全局锁**。如果查询期间有新成绩提交，名次、总人数或上一名可能出现轻微快照差异（例如名次短暂偏差 1 名）。这是低成本排行榜的明确取舍，刷新后会收敛；接口不会因此返回虚构名次。
- 前 100 名在客户端缓存 60 秒；仅在云端最佳确实变化时主动失效，避免普通页面进入造成重复请求。个人排名不缓存，避免刚刷新最佳后仍显示旧名次。
- 排名展示名是 `_id` 哈希的前 10 位十六进制字符，稳定且不直接暴露 openid；它不是实名昵称，也不应被当作账号标识。
- 仍存在的竞态风险：限流判断不是原子的，极端并发下可能放行超过每秒一次的提交；并发首次创建后的条件更新窗口依赖数据库单文档原子性；客户端与云端状态最终一致，但不保证严格线性一致。
- 客户端计时成绩本身可以被伪造；服务端范围校验、限流、确定性排序和条件计数不能证明成绩真实，本项目不宣称具备完整防作弊能力。
- 日志不输出完整 `openid` 或敏感数据。
